1. How to use this document

This document is the single source of truth for what the team builds; where it disagrees with the existing prototype code, this document wins, unless an item is marked DECISION PENDING.

Humans: read sections 2 to 4 for context, then sections 11 and 16 to see what to do first.

LLM coding assistants: paste the whole document into the context, then work on one milestone at a time (section 16). Follow these rules:

    Do not add features outside section 4. If a feature seems missing, propose it as a question instead of building it.

    Keep the scheduling engine a pure, deterministic JavaScript module: no DOM, no network calls, no randomness, no LLM calls inside the engine.

    Before changing any scoring constant, classification rule or default, update the matching golden test in section 10 first, then the code.

    After every change, run node --test and report which numbered acceptance tests (T1, T2, ...) pass or fail.

    If something is ambiguous, list the ambiguity and propose the smallest reasonable option. Do not invent product behavior.

    Never let any code path apply a change that needs someone else's approval (professor, teammate) as if it were granted. See section 13.

    Never place work in the protected sleep window. See section 13.

2. Product in one page

The 25th Hour is a commitment decision-support tool that tells a student what their next "yes" will cost, and the smallest change that makes it fit, while protecting sleep as a hard scheduling constraint.

Tagline: Know what your next yes will cost.

Problem. University students take on coursework, clubs, research and internships without checking whether the hours exist before each deadline. A weekly hours total can look fine (18h of work in 20h of time) while a deadline is already impossible (15h due by Thursday, 13h available by Thursday). Sleep is the first thing sacrificed.

Core insight. Warnings alone do not change behavior; students already know they are busy. The product must act at the moment of decision ("should I say yes?") and, when the schedule is infeasible, show the least disruptive verified fix.

The loop: Decide (F1 Commitment Check) → Adjust (F2 Rescue Engine) → Learn (F3 Reality Feedback).

Design principles (non-negotiable)

    Be honest: if a schedule is impossible, say so. Never pretend rescheduling creates hours.

    Sleep is protected by default; the student can still override, and an override leaves the conflict visible.

    Student autonomy: recommend and explain, never force.

    Minimal effort: a check needs name, hours, deadline and one priority tag. Setup is a one-time import.

    No guilt mechanics: no streaks, leaderboards, or penalties for sleeping less than planned.

    Verified, not guessed: every suggested change is re-run through the scheduler before it is shown.

    Privacy: data stays on the student's device in the MVP. Professors and teammates need no accounts; requests go out as ordinary messages the student sends.

What this product is not: a sleep tracker, a gamified rewards app, a chatbot, a generic calendar, a medical or anxiety/insomnia treatment, or a surveillance tool for universities.

What is unproven (do not claim these in the demo): that students act on the suggestions, that sleep improves, that this beats existing schedulers in real use, and that universities will pay. The prototype proves only the technical claim: a deadline-aware engine catches a conflict that a weekly total misses and finds a verified fix.

5. Domain model

These shapes match the existing engine code; fields marked NEW are additions for F1 and F3. Keep the engine's inputs and outputs as plain JSON-serializable objects so they can be stored and tested.

  id: string;                     // unique

  type?: TaskType;                // NEW, used for estimate learning

  max: number;                    // conservative hours

  flexible: boolean;              // target may move up to hardDay without anyone's approval
  allowDrop: boolean;             // task is genuinely optional (droppable)
  splittable: boolean;            // MUST be true in the MVP (scheduler throws otherwise)
  canRequestExtension?: boolean;  // hard limit could be asked to move by +1 day (needs approval)
  reduceBy?: number;              // hours of scope that could be cut
  reductionNeedsApproval?: boolean;

// ---------- Engine outputs ----------
type Verdict = 'feasible' | 'at-risk' | 'infeasible';

interface Alloc {                 // one 30-minute slot assigned to a task
  date: string; dayIndex: number; start: number; end: number;   // minutes since midnight
  label: string; taskId: string; taskTitle: string; minutes: number; late: boolean;
}

interface TaskResult {            // all durations in MINUTES
  id: string; title: string; required: number; scheduled: number; missing: number;
  late: number; shortByDeadline: number; dueDay: number;
}

interface DeadlineMargin { dayIndex: number; capacity: number; demand: number; margin: number } // minutes; margin = capacity - demand, cumulative up to that day

interface ScheduleResult {
  feasible: boolean;              // true iff every task finishes by its deadline (no misses)
  lateMinutes: number; requiredMinutes: number; capacityMinutes: number;
  alloc: Alloc[]; byDay: { date: string; index: number; capacity: number; assigned: Alloc[] }[];
  taskResults: TaskResult[]; misses: TaskResult[]; deadlineMargins: DeadlineMargin[];
}

interface Evaluation {
  verdict: Verdict; reason: string; minMargin: number;   // minMargin in minutes, at conservative estimates
  optimistic: ScheduleResult; typical: ScheduleResult; conservative: ScheduleResult;
}

// ---------- Rescue Engine ----------
type ActionType = 'move' | 'drop' | 'reduce' | 'extend';

interface Action {
  id: string;                     // e.g. "move:poster:4", "drop:research", "extend:poster:4"
  taskId: string; type: ActionType;
  toDay?: number;                 // move, extend
  amount?: number;                // reduce, hours
  needsApproval: boolean;         // true for extend, and reduce when reductionNeedsApproval
  label: string; description: string;
  impact: number;                 // minutes of work affected (informational)
  disruption: number;             // move 1, extend 2, reduce 3, drop 5
}

interface Repair {
  id: string;                     // action ids joined by "+"
  actions: Action[];              // 1 or 2 actions on different tasks
  updated: Task[];                // the tasks as they would be after the repair
  test: Evaluation;               // the re-run evaluation of the updated tasks
  needsApproval: boolean; score: number;     // lower score ranks first
}

// ---------- F3 Reality Feedback (NEW) ----------
interface TaskFeedback {
  taskId: string; type: TaskType; estimatedLikely: number; actualHours: number; // actualHours multiple of 0.5
  recordedAt: string;             // ISO timestamp, local
}

interface SleepReport {           // optional, one tap, never required
  date: string;                   // the night ending on this morning
  hoursSlept: number;             // multiple of 0.5
  stress?: 1 | 2 | 3 | 4 | 5;

}

interface EstimateProfile {       // per task type, learned from TaskFeedback
  type: TaskType; samples: number; ratio: number;   // ratio = smoothed actual / estimated, clamped to [0.5, 3]
}

6. Algorithms

The engine is a deterministic pipeline: build capacity, schedule with earliest-deadline-first, classify at three estimate levels, then search for verified repairs. Everything below [EXISTS] unless marked [FIX] or [NEW].
6.1 Build capacity (slots)

for each day:
  for each workWindow [begin, end):
    for each 30-minute slot m in the window:
      skip if the slot overlaps the sleep window (handle wrap-around, e.g. 23:00-07:00)
      skip if it overlaps any busyWindow
      skip if this exact slot was already added (overlapping windows)
      add slot {date, dayIndex, start=m, end=m+30}
sort slots by (dayIndex, start)

Sleep is removed from capacity before anything else, so no code path can schedule work inside it.
6.2 Deadline-aware scheduler

Inputs: tasks, days, estimate in {optimistic, typical, conservative}, deadline in {target, hard}. Duration of a task = min, likely or max hours times 60. The deadline day of a task = targetDay or hardDay.

remaining[task] = duration minutes
for each slot in time order:
  eligible = tasks with earliestDay <= slot.dayIndex and remaining > 0
  if none: continue
  pick = min(eligible) by (deadlineDay ASC, priority ASC, id ASC)     // earliest deadline first
  used = min(30, remaining[pick]); remaining[pick] -= used
  record alloc {slot, task: pick, minutes: used, late: slot.dayIndex > deadlineDay(pick)}
for each task:
  shortByDeadline = required - minutes allocated on or before its deadline day
feasible = (no task has shortByDeadline > 0)

Why EDF: for work that can be split into equal slots, with release days and deadlines, earliest-deadline-first finds a feasible schedule whenever one exists. This is what makes the feasibility claim trustworthy and is covered by a property test (T11). Tasks are always treated as splittable in the MVP.
6.3 Deadline margins (explanation numbers)

For every distinct deadline day D present in the task set:

capacity(D) = total free minutes on days 0..D
demand(D)   = sum of durations of tasks whose deadline day <= D
margin(D)   = capacity(D) - demand(D)        // negative = shortfall at that deadline

The binding day is the deadline day with the smallest margin. The interface must show the binding day's demand and capacity in words (for the demo: "Work due by Thursday: 15h. Time available by Thursday: 13h."). [FIX] B4.

Note: margins ignore earliestDay; the scheduler is the source of truth for feasibility, margins only explain it.
6.4 Classification

Run the scheduler three times (optimistic, typical, conservative) against target deadlines.

This deliberately ignores deadlines. It exists only to show what a naive planner would conclude. Label it as a simulated baseline, not as any named product.

6.7 Approval gate

A repair with needsApproval = true is only a preview and a drafted message. The plan changes only when the student explicitly records that the other person agreed (in the demo: the button "Simulate approved request"). Preview functions must not mutate application state or the task list (test T13).

Behavior

    On submit, create a task with isProposal = true (not yet part of the plan).

    Evaluate twice: the plan without the proposal and with it. Show both verdicts side by side.

    If the plan with the proposal is not feasible, call the Rescue Engine (F2) and show its top repair inline.

    The student chooses one of: Accept (proposal joins the plan, isProposal = false), Accept with suggested change (applies a self-serve repair, then accepts), Accept anyway (override; see below), Not now (discard). Nothing is added to the plan until one of the accept options is chosen.

    Accept anyway is always allowed. The conflict stays visible on the main screen as an unresolved banner until the student resolves it or the deadline passes. The app never blocks or scolds.

Output: the cost statement (plain language, generated from numbers, no LLM)

Without this:  Feasible. Tightest deadline: Tuesday, 3h to spare.
With this:     Infeasible. Work due by Thursday: 15h. Time available by Thursday: 13h. Short by 2h.
Tasks due by Thursday: DBMS Lab (4h), ML Assignment (3h), AUV Club Poster (3h), New Research Project (5h).

The numbers come from the binding deadline margin (section 6.3), not from the weekly total. Never blame a single task for a shortfall that comes from several tasks sharing a deadline (B4).

7.2 F2 Rescue Engine ("Make it work")

Purpose. When the plan is infeasible or at risk, list the few smallest verified changes, ranked, and separate what the student can do alone from what needs another person.

Behavior

    Algorithm: section 6.6, including fixes B2 and B5. Show at most 5 repairs in the interface (engine returns up to 10).

    Every repair card shows: the change in one sentence; number of changes; badge Self-serve or Needs approval (pending); the verdict after the change; the binding-day margin after the change; a preview of the repaired timeline.

    Self-serve repair: button "Apply". On apply, store the change, recompute, and show a confirmation with the new verdict. Allow "Undo" for the last applied change.

    Approval repair: buttons "Copy request text" and, once the student has heard back, "Mark approved" or "Mark declined". Until marked approved, the real plan, deadlines and verdict do not change. The preview is labelled "If approved".

    Request text templates (plain text, copy to clipboard, never sent by the app):

        Extension: states the task, the proposed new date, that the current deadline stays in effect until approved, and a thank-you. Include the student's own numbers only if the student ticks "include my workload summary".

        Scope reduction: states the task, the hours of optional work proposed to cut, and that current scope stays until agreed.

    If no verified repair exists, say so plainly: "No verified fix with the changes you've allowed. This is a capacity problem, not a scheduling problem." and suggest the student mark something droppable or flexible. Do not invent options.

    Never describe a repair as solving the conflict unless the re-run shows typical.feasible = true.

7.3 F3 Reality Feedback ("Did it work?") [NEW]

Purpose. Close the loop: make estimates more accurate over time and check whether the plan actually protected sleep, with almost no effort from the student.

Task feedback

    When a task's target day passes, or the student marks it done, ask once: "How long did it actually take?" with a stepper preset to the typical estimate. One tap on "As planned" confirms. Value is a multiple of 0.5 hours.

    Store a TaskFeedback record. recordedAt is the completion time and may be edited by the student.

Estimate learning

ratio_n = 0.6 * ratio_(n-1) + 0.4 * (actualHours / estimatedLikely)     // per TaskType, ratio_0 = 1
ratio is clamped to [0.5, 3]
samples < 3  -> do not change any estimates; show "learning (1 of 3)"
samples >= 3 -> when the student enters a new task of that type, show the adjusted estimate
                 next to their own: "You said 4h. Your last 3 problem sets took 1.4x your estimate. Use 5.5h?"
                 The student's number is kept unless they tap the suggestion. Round to 0.5h.

Never change a student's entered estimate silently. Always show where an adjusted number came from.

Sleep and stress report (optional)

    One optional prompt per morning: hours slept (stepper in 0.5h steps) and optional stress 1 to 5. Skippable without consequence. At most one prompt per day. No streaks, badges, or reminders beyond that single in-app prompt.

    plannedSleepMinutes is the length of the protected sleep window at the time of the plan (8h for 23:00 to 07:00).

"Did it work?" view (one screen, for the last 7 days)

    Adjustments applied (what changed, self-serve or approved, date).

    Deadlines: met or missed per task (based on completion time vs target and hard day).

    Estimate vs actual per task, with the learned ratio per type.

    Reported sleep vs planned sleep opportunity per night, only for nights the student reported.

    One neutral sentence, e.g. "Your plan kept your sleep window free on 5 of 5 days. You reported 6.5h on average on the 4 nights you logged." Always followed by: "A feasible plan makes room to sleep; it can't guarantee sleep."

No scores, no ranking, no comparison with other students.

Freshness (important for trust)

    Store two separate timestamps: calendarImportedAt (when imported data was loaded) and lastEditedAt (any change in the app). Show the first on the verdict card: "Based on your calendar from [time]." [FIX] B7.

    If no calendar was imported, or the import is older than 24 hours, show a banner above the verdict: "Your calendar may be out of date. Re-import before relying on this." Do not block.

Interaction and quality rules

    Recompute the verdict on every input change; recomputation must finish within 100 ms for 5 weeks and 30 tasks.

    Verdict region uses aria-live="polite" so screen readers announce changes.

    Every control is keyboard operable; touch targets are at least 44 px; layout works from 360 px width.

    Text contrast meets WCAG AA. Timeline slots have text alternatives (task, time, late or free) through title/aria-label.

    Errors from the engine (invalid input) are shown as a plain message next to the offending field. A thrown error must never leave a blank screen.

    All state changes go through one function that updates the state object and re-renders. No hidden global flags (the prototype's appliedActions, extraTasks, extraEvents arrays should become fields of that state object).

9.2 Calendar file (.ics) [EXISTS] + extensions

Supported today: VEVENT blocks with explicit DTSTART and DTEND as floating local time (20261116T170000), UTC (...Z, converted to Asia/Kolkata), or TZID=Asia/Kolkata. Line unfolding is handled. Strongly recommended [NEW]: expand simple weekly recurrence (RRULE:FREQ=WEEKLY;BYDAY=MO,WE;UNTIL=... or COUNT, with INTERVAL and EXDATE) for the loaded weeks. A class timetable exported from Google Calendar or a university system is almost always recurring, so without this the "import your timetable" promise fails for real files. Unsupported recurrence patterns keep producing a warning.

13. Non-functional requirements and safety rules

These rules are not optional: they protect the student's trust and keep the engine's claims honest.

Safety rules (never break these)

    Sleep is never used for work. The scheduler removes the protected sleep window before allocating. No repair may shrink the sleep window. The window changes only when the student edits it in Settings.

    No silent changes to deadlines. A change that needs another person's approval never affects the evaluated plan until the student records that it was approved. The app never sends messages; it only drafts text to copy.

    No false reassurance. The interface says "fits" only if the typical estimate fits, and never states or implies that a feasible plan guarantees sleep or lower stress.

    No dark patterns. No streaks, scores, badges, countdown pressure, or guilt wording about sleep. At most one optional in-app prompt per day (the morning sleep report).

    Override is always allowed. A student can accept a commitment the engine says is infeasible; the conflict stays visible, nothing is blocked or hidden.

Privacy

    All data stays on the student's device (browser storage under a versioned key such as the25thhour.v1). The page makes no network requests after it loads: no analytics, no third-party scripts, fonts or images. A browser test asserts this.

    Provide "Clear all my data" in Settings. Optional CSV export is manual and initiated by the student.

    Store the minimum: task fields, applied changes, feedback and sleep reports. Do not store imported event titles beyond what the screen needs.

    Professors and teammates never see any student data unless the student copies a message to them. Copy only the numbers the student ticks.

    Show this notice on first run: "This is a planning tool, not medical advice, and not a treatment for sleep or anxiety problems."

Engineering

    Determinism: the same inputs must give the same outputs. The engine must not call Date.now(), new Date() without an argument, Math.random(), or anything locale-dependent. Replace a.id.localeCompare(b.id) with a plain < / > comparison (locale-independent tie-break).

    Time: the engine works on date strings (YYYY-MM-DD) and minutes since midnight, never on local-time Date objects. Time-zone conversion happens only in the importer, with explicit Asia/Kolkata handling, so results do not depend on the browser's time zone.

    No runtime AI: no LLM or network calls in the product. LLM assistants may be used during development only.

    Structure: engine is a pure ES module with no DOM access; the interface imports it and holds one state object (section 8). No global mutable variables outside that state.

    Browsers: current Chrome, Edge, Firefox and Safari; no build step required to run; no runtime dependencies. Dev dependencies allowed: a test runner and Playwright.

    Versioned storage: include a schemaVersion in stored data and a migration function; a version mismatch must never crash the page (fall back to a clean state and tell the student).

    Errors: engine functions throw Error with a human-readable message for invalid inputs; the interface catches it and shows it beside the field.

Meaning

Feasible / at-risk / infeasible
	

The three verdicts (6.4); feasible means every deadline is met even at conservative estimates with at least 60 minutes of slack

Margin
	

Free minutes up to a deadline day minus the minutes of work due by then; negative means short

Binding day
	

The deadline day with the smallest margin; the day the verdict message talks about

Cushion
	

The 60 minutes of conservative slack required for a feasible verdict

EDF
	

Earliest deadline first: the scheduling rule that always works on the task with the nearest deadline

Slot
	

A 30-minute block of free time

Protected sleep window
	

The hours (default 23:00 to 07:00) that are never offered as work time

Proposal
	

A commitment the student is considering but has not accepted (isProposal = true)

Repair
	

A set of one or two changes that, when re-checked, makes the plan better

Self-serve change
	

A change the student can make alone (move a target, decline an optional task)

Approval-dependent change
	

A change that needs a professor or teammate (extension, scope reduction); stays hypothetical until the student records the answer

Scheduling problem vs capacity problem
	

A scheduling problem can be solved by reordering within existing flexibility; a capacity problem has more required work than available time and needs a task dropped, reduced or extended

Golden test
	

A test whose expected values are fixed in this document (section 10)

Concierge test
	

Running the engine by hand for a few real students to see whether they act on the output, before building more

Simulated baseline
	

The weekly-hours and deadline-aware comparison cards, produced by this project's own code and not by any named product
